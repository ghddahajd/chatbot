# Скрипты

Роль каждого скрипта — чтобы при рефакторинге и подготовке клиента №2 было видно, что можно
трогать свободно, а что завязано на живой процесс. Ничего отсюда не удалять и не переносить
без явного решения — `test_scripts_help.py` проверяет, что все скрипты с `argparse` хотя бы
запускаются (`--help`), это не проверка их логики.

## Онбординг нового клиента

| Скрипт | Что делает |
|---|---|
| `create_kb_draft.py` | создаёт черновик клиентской KB из шаблона и исходных материалов |
| `validate_kb.py` | проверяет клиентскую базу знаний без запуска backend и зависимостей |
| `onboard_client.py` | публикует проверенную KB клиента в рабочую папку и печатает embed |
| `client_launch_check.py` | проверяет готовность опубликованного клиента к запуску |
| `db_admin.py` | отдельная проверка PostgreSQL и повторяемая регистрация клиентских KB; не переключает runtime |
| `client_accounts.py` | создание, отключение и сброс пароля сотрудника; отдельная роль БД для клиентского входа |
| `lead_storage.py` | скрытый ввод пароля и выдача отдельной ограниченной роли для лидов и generic outbox; runtime не переключает |
| `analytics_storage.py` | создание отдельной роли синхронизации аналитики со скрытым вводом пароля |
| `import_lead_history.py` | пробная проверка и импорт JSONL заявок, подготовка файла для отката из PostgreSQL |
| `lead_cutover.py` | счётчики файловых очередей, снимок остановленного backend и сверка импорта с PostgreSQL |
| `check_lead_startup.py` | проверка полного старта backend с PostgreSQL в одноразовом контейнере, с отключёнными отправками |
| `check_analytics_import.py` | локальный импорт и догрузка событий одной клиники из неизменяемой копии JSONL. Нужны зависимости БД, миграция и реестр в тестовой базе `ANALYTICS_DATABASE_URL`. По умолчанию проверяет вход, `--apply` пишет события. Для сверки воронки добавьте `--start`, `--end` (UTC) и `--leads`. Сверяемый период должен целиком присутствовать в JSONL. |
| `crawl_article_batch.py` | краулит staging batch статей и режет текст на chunks для будущего RAG |
| `import_articles_registry.py` | импортирует реестр статей клиента в staging без публикации в runtime KB |

Для локальной автоматической догрузки запустите один экземпляр backend с SQL-зависимостями,
`ANALYTICS_SYNC_ENABLED=true` и параметрами подключения `ANALYTICS_*` в окружении процесса.
По умолчанию интервал 300 секунд, его меняет `ANALYTICS_SYNC_INTERVAL_SECONDS`.
Примените миграции и зарегистрируйте клиники в тестовой базе заранее. При сбое догрузки
очистка JSONL ждёт следующего успешного цикла.

Для проверки SQL-воронки в локальном бекстейдже дополнительно задайте
`ANALYTICS_SQL_FUNNEL_ENABLED=true`, а для графиков по часам и дням недели —
`ANALYTICS_SQL_ACTIVITY_ENABLED=true`. Для топов вопросов и разбивок по намерениям
и возражениям задайте `ANALYTICS_SQL_QUESTIONS_ENABLED=true`. Для отчётов по операторам и
ожиданию в очереди задайте `ANALYTICS_SQL_OPERATORS_ENABLED=true`. Для сводки, тренда
непонятых вопросов и сравнения периодов задайте `ANALYTICS_SQL_SUMMARY_ENABLED=true`.
API использует события последней синхронизации. Владелец может открыть отчёт по всем
клиникам из SQL вместе с историческими идентификаторами вне реестра. Если в JSONL
есть события без корректного идентификатора компании, общий отчёт читает файл целиком. Графики используют
также синхронизированные исторические сводки. При изменении файлов, ошибке или таймауте используется
файловый расчёт. При всех пяти флагах и актуальном полном снимке SQL-дашборд
пропускает чтение обоих файлов аналитики.

## Ежедневная проверка и отладка

| Скрипт | Что делает |
|---|---|
| `preflight.py` | одна команда «всё ли на месте»: отчёт `/api/debug/preflight`, красные линии, взгляд снаружи |
| `policy_snapshot.py` | сеть безопасности перед правкой правил: одни и те же сообщения через две версии кода, список различий и покрытие исходов |
| `dialog_snapshot.py` | сеть безопасности, диалоги целиком через HTTP: две версии кода по ходам диалога + красные линии |
| `debug_trace_batch.py` | пакетно прогоняет конфликтные сообщения через internal debug trace |
| `export_dialogs.py` | вытаскивает переписки по префиксам session_id в один текстовый файл |
| `smoke_ai_scenarios.py` | smoke-матрица AI/policy сценариев для любого опубликованного клиента |
| `run_ai_evals.py` | baseline eval runner для качества AI/policy понимания фраз |
| `vendor_compare.py` / `demo_gate.py` | сравнение с примерами диалогов вендора; `demo_gate` — та же проверка перед демо |
| `send_test_delivery.py` | отправляет тестовое delivery-событие для проверки каналов клиента |
| `smoke_managed.py` | smoke-проверка managed-service flow через FastAPI TestClient |
| `smoke_onboarding.py` | smoke-проверка полного onboarding flow без Docker и реальных клиентов |
| `smoke_article_retrieval.py` | проверяет retrieval по staging article chunks без embeddings/pgvector |
| `simulate_kb.py` | прогоняет тестовые вопросы на клиентской KB без запуска Docker |
