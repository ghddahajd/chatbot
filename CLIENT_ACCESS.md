# Персональные доступы клиник

Клиентский вход выключен по умолчанию (`CLIENT_LOGIN_ENABLED=false`). Обычный образ,
вход владельца и файловые хранилища продолжают работать. Переписки, заявки, KB и
аналитика в PostgreSQL этим этапом не переносятся.

## Разделение доступа

- Владелец использует прежний служебный пароль и видит бекстейдж всех клиентов.
- Сотрудник входит с персональным логином и паролем, назначается одной клинике.
- `/analytics`, чаты, заявки и настройки ограничены клиникой из сессии входа.
- Подмена company_id запрещена, чужая переписка по ID возвращает 404.
- Выгрузка с ID разных клиник включает только свою клинику.
- `/backstage`, debug, delivery и старые операторские HTTP/WebSocket API остаются только владельцу.
- Скрытие селектора не является защитой: ограничения применяются и к прямым API-запросам.

Мастер-пароль владельца не передавать сотрудникам: он сохраняет полный доступ.
Публичный протокол посетительского виджета в этом этапе не меняется.

## Подготовка локального контура

Сначала выполнить подготовку из STORAGE_FOUNDATION.md в выбранном Compose-проекте.
Ниже то же имя проекта `chatbot-storage`; использовать одно имя для БД, инструментов
и backend. Не пытаться запускать второй backend с именем уже работающего контейнера.

```bash
docker compose -p chatbot-storage -f docker-compose.storage.yml build db-tools
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools alembic upgrade head
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools python scripts/db_admin.py register-clients
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools python scripts/client_accounts.py grant-runtime
```

Последняя команда скрыто запросит отдельный пароль роли `chatbot_client_runtime`.
Она получает чтение реестра/учётных записей и чтение, создание и удаление сессий входа.
Не получает изменение учётных записей, удаление клиентов или создание таблиц.
Вход сотрудников откажет, если ошибочно подключить его с owner-ролью.
Управление учётками выполняется отдельными инструментами с доступом владельца БД.

## Учётные записи

```bash
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools python scripts/client_accounts.py create --login clinic-admin --company-id CLINIC_ID
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools python scripts/client_accounts.py disable --login clinic-admin
docker compose -p chatbot-storage -f docker-compose.storage.yml run --rm db-tools python scripts/client_accounts.py reset-password --login clinic-admin
```

Заменить CLINIC_ID на зарегистрированный идентификатор. Пароль — 12–128 символов,
вводится скрыто с подтверждением, без аргументов командной строки. Команды создания,
смены пароля и выдачи DB-роли требуют интерактивный терминал.
Отключение или сброс пароля отзывает существующие сессии; сброс не включает отключённую учётку.
Повторное создание существующего логина отклоняется. Смена клиники существующей учётке
не поддерживается: создать отдельную учётку и отозвать старую.

## Включение backend

Выбрать сборочную цель `client-access` и явно подключить `docker-compose.client-access.yml`
к основному Compose и storage-файлу в одном проекте. Для локальных клиентских данных
сохранить обычный docker-compose.override.yml. Основной Compose сам вход не включает.

В zsh задать **тот же** пароль runtime-роли, который введён в grant-runtime:

```zsh
read -rs 'CLIENT_DB_PASSWORD?Пароль runtime-роли БД: '; echo
export CLIENT_DB_PASSWORD
```

Overlay передаёт runtime-роли PGUSER/PGPASSWORD и обнуляет возможный owner DATABASE_URL
из базового .env. Основной backend получает доступ и к своей обычной сети, и к закрытой
storage-сети. PostgreSQL не получает публичного порта. Не использовать storage_owner
для запросов приложения. Пароли не печатать через `docker compose config`.
Overlay использует `!reset`: нужен Docker Compose с поддержкой этого тега.
Он снимает прежний network_mode у backend. Если на сервере использовалась host-сеть,
перед включением отдельно проверить Telegram через действующий прокси в новой сети.
В этом этапе сеть работающего контейнера не переключается.

Клинические страницы требуют существующий HTTPS с сохранением Host и X-Forwarded-Proto.
Локальный DEV_MODE допускает HTTP. При включённом входе форма показывает логин сотрудника;
для прежнего входа владельца логин оставляют пустым.

Сессия по умолчанию действует 24 часа (`CLIENT_LOGIN_HOURS`, 1–168). Cookie HttpOnly,
SameSite=Lax, Secure на HTTPS и для клинического входа вне dev-режима. В БД хранится
только хеш случайного идентификатора. Изменения проверяют Origin/Referer; запросы без
подтверждения своего origin отклоняются. Ограничение входа — 10 попыток в минуту на IP
в одном процессе приложения. При нескольких процессах потребуется общий лимитер.

Если БД входа недоступна, клиентские запросы получают 503, без перехода на общий доступ.
Вход владельца и публичный чат не используют эту БД. При неудачном отзыве сессии logout
возвращает 503, очищает локальные cookie, но не обещает успешный отзыв на сервере.

## Проверки и откат

Обычные проверки — по AGENTS.md. Отдельные PostgreSQL/HTTP-тесты:
`backend/tests/test_client_access_postgres.py`, запускать с `DB_INTEGRATION_TEST=1`
в изолированном контуре с runtime-доступом, тестовыми KB и TEST_OWNER_DATABASE_URL
для создания/удаления исключительно временных учёток. В обычном pytest этот модуль пропускается.

Перед изменением рабочей БД — копия и проверенное восстановление по STORAGE_FOUNDATION.md.
Сначала применяется миграция 0002_client_access, потом включается клиентский вход.
Для отключения входа достаточно убрать overlay/выключить CLIENT_LOGIN_ENABLED: backend
снова не импортирует SQL-зависимости, клиентские cookie перестают предоставлять доступ.
Не запускать downgrade на рабочей БД для отката кода: он удаляет учётки и сессии входа.
Обычные посетительские переписки и заявки эта миграция не затрагивает.
